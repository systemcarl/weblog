# DevLog: Listing Articles With a Simple Index
It doesn't really make much sense to have a weblog without any way to browse
    articles.
Unless links to each and every article are hard coded into the website,
there needs to be a regularly updated list of articles living somewhere, that
    can be used to display article listings dynamically to the user.
A list of articles can easily be implemented with database to store and map
    article metadata.
But unless that database is on the user's device
    (it's possible with something like [IndexedDB], but not always practical),
the list of articles must be compiled to an index of some sort and served to the
    user's browser, or other client.

When adding a way to list and highlight articles to my personal website
([this one] you're likely on right now),
I wanted to keep the solution as simple as possible.
At the time, the application was effectively stateless
— there was no database or server-side storage.
All of the articles and their associated content were stored as markdown files
    in a public git repository and [rendered on-demand] into nice web pages.
Ideally, this indexing the articles would not require deploying and maintaining
    a database, alongside the web application, to list and sort the articles.

## If You Want Something Done Quick
Since I knew exactly what needed to be included in the article listings
    (for now, at least),
it was easy enough to just compile [a simple index file] myself (by hand) to map
    out the entire article repository.
It also helped that the article repository was still quite small
    (only 8 articles at the time).
It didn't take long to create a list of all the articles, group them into a
    couple of categories
(literally just two at the time, [DevLogs] and everything else),
and add a title and summary to display in the article listing.

### Thinking Inside the Box
It wouldn't have been too much harder to have the index generated by the
    application fetching and rendering the articles.
Since the structure of the article repository was well-defined,
    the application could have scanned the repository and requesting each
    article file to extract the necessary data.
The index could then be temporarily stored in-memory in the application, to
    cache the results,
avoiding excessive calls to the article repository and limiting the number of
    long-running aggregation processes.

While it would have been nice to not have to maintain the index file manually,
    there were some good reasons not to implement this approach.
Obviously, it would have added unnecessary complexity to the application,
    requiring significantly more logic for traversing the article repository.
But more importantly, it would have made the application responsible for
    indexing the articles.
The purpose of the application is to display the content as it's provided,
not to manage or curate it.
By keeping the article indexing separate from the web service,
    the content can be managed independently,
and possibly be used by other application or services with consistent indexing
    and metadata.

## A Couple of Considerations
Knowing when and where the article index would be created was only half the
    problem.
To make the index useful and effective, forethought needed to be given to how
    the index should be structured,
especially if the index is being maintained manually.

Since the index is also being maintained externally,
this becomes a tight coupling between the application and the content data.
Maintaining the articles and the index separately has advantages,
but it comes with no guarantee that the application and the article data will
    remain compatible
— something I had considered when first [integrating the Markdown articles] into
    the application.
To avoid issues as the application and article repository evolve independently,
the index structure needs to be simple and resilient against changes either to
    the application or articles themselves.

### That Page at the Back of a Book
The idea of a [publishing index] is nothing new.
Many books include an index at the back to help readers locate topics of
    interest.
Traditionally, an index maps keywords
    (*e.g.*, names, places, or abstract concepts)
    to page numbers or sections within the book
— painstakingly compiled by a specialized [indexer] or the author themselves.
There seemed no reason to reinvent anything here.

To accomplish my immediate goals of listing articles by category with some basic
    metadata,
the index only needed to map category tokens (or tags) to the article slug
    (the URL path identifier for each article page).
[Javascript Object Notation (JSON)] is an easy way to represent data with
    key-value pairs and nested structures,
so it made sense to add a simple `.json` file to the root of the article
    repository to hold the index data.
The index file would contain the necessary metadata for every listed article
and assign each article to one or more categories.

Interestingly, many full-text search engines also use similar indexing
    techniques to map every word in the document corpus to the documents that
    contain them.
Naturally, these indexes are much longer and more complex.
To anticipate incomplete terms or input typos, search indexes often employ
    techniques, like stemming or prefix matching, to improve search results,
greatly increasing the size of the index.
Maintaining a comprehensive full-text search would require some sort of
    tokenization algorithm to generate an effective index
— it would be nearly impossible to maintain such an index manually for even a
    small article repository.

### Playing the Meta
Exactly what metadata should be included in the article index is also a detail
    worth considering.
Any metadata can either be relevant to the article itself, or the index listing,
    depending on how each will be displayed.
The article title, author, publication date, meta tags, and descriptive summary
    may or may not be needed to render the article page or it's listing in the
    index.
Duplicating the metadata in both the index and the article files is not ideal,
as it can easily lead to inconsistencies without processes to keep them both
    aligned.

However, the problem becomes how common metadata
— the information displayed both in the index and the full article —
will be accessed.
It's obvious to include the common metadata in index data to preclude the need
    to query each article file when rendering every article listing.
But this still means that index data must be fetched whenever an article page is
    requested as well, to provide all of the necessary metadata.
Requiring an additional query to satisfy every page request is generally bad for
    performance and reliability,
causing issues if the query becomes slow or fails altogether.

I opted to still include common metadata in each article file.
Eventually, the article repository would be served from a more sophisticated
    service
that automatically resolves an articles metadata for consistency across all
    contexts.
While the article repository is still quite small,
the time it takes to maintain the redundant data is negligible,
and small inconsistencies that may arise are not likely to ever be noticed.

## Capping the Requests
I raise all of these considerations because when designing any effective system,
it's important to understand how the system will be used.
When querying large sets of data over a network, from a set of documents or any
    other source,
the basic functional requirements (what will be requested) is not enough to
    deliver a workable solution.
Knowing how often and in what manner the system will be used — the user
    behaviour — must also be considered,
especially if requested information requires processing or is not otherwise
    trivially available.
In many cases, it's also important to not just think about how you intend users
    to make requests,
but also how bad actors (*i.e.*, malicious users) might abuse the system.

Almost immediately after implementing the article highlights on my
    [personal website],
the rate limits of the article repository were reached.
It had not occurred to me that every request, including invalid requests for
    non-existent resources (404s), would still load all the required application
    data — including the article index file.
Instead of just the few dozen legitimate requests I was expecting each day,
    the index file was being requested hundreds of times per minute
to serve the persistent bombardment of requests I regularly received from
    potential hackers scanning for vulnerabilities.
This was more than enough to exhaust the article repository's rate limit,
    making all article content and data unavailable across the entire website.
Realizing this mistake, I rushed to quickly implement caching for the index file
    and all the other static assets,
limiting the maximum number of requests the application could make to any
    resource within a specified time period.
While there was no damage done,
it was an embarrassing reminder that any networked system really should have
    some throttling or other rate-limit protections in place,
regardless of scale.
