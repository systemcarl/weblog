# DevLog: Listing Articles With a Simple Index
It doesn't really make sense to have a weblog without any way to actually
    browse articles.
Unless links to each and every article are hard coded into the website,
browsing requires there to be an up-to-date list of articles living somewhere,
that can be used to display article list entries to the user upon request.
A list of articles can easily be implemented with a database to store and map
    article metadata.
But unless all the articles are in a database on the user's device
(which is possible with something like [IndexedDB], but not always practical),
an abbreviated list of articles must be compiled to an [index] of some sort and
    served to the user's browser (or other client)
— simply sending the entire repository of articles for every request would be
    slow and costly in most cases.

Up until [this update], my personal website had no list of articles at all.
The only way to find an article was through direct links from other places I
    had left them: [GitHub], [Mastodon], [BlueSky], *etc.*
This was fine to get started, since the list would look pretty sad with only a
    few articles.
However, if I ever wanted anyone to read my increasing number of articles,
or use [the open source web application] I was building to serve it,
I needed to add a means to list the available articles in a meaningful way
    — sorted and curated into categories.

I wanted to keep the indexing solution for my application as simple as possible.
The application is effectively stateless
— there is no database or other server-side storage.
All of the articles and their associated content are instead stored as Markdown
    files in [my public weblog Git repository].
These files are all [rendered on-demand with SvelteKit] into HTML
    [via an integrated Markdown parser].
Ideally, indexing the articles would not require deploying and maintaining a
    database to store the compiled index.

## If You Want Something Done Quick
Since I knew exactly what needed to be included in the article list entries
    (for now, at least),
it was easy enough to just compile [a simple index file for all my articles]
    by hand to map out the entire article repository.
It also helped that the article repository was still only 8 articles.
It didn't take long to create a list of all the articles, group them into a
    couple of categories
(literally just two at the time, [DevLogs] and [everything else]),
and add a title and summary to be displayed for each article listed.

### Thinking Inside the Box
It wouldn't have been too much harder to have the index generated by the
    application fetch and render the articles.
Since the structure of the article repository is well-defined,
    the application could scan the repository directories and request
    each article file to extract the necessary [metadata]
    (the title, summary, and tags in this case).
The index could then be temporarily stored in-memory in the application, to
    cache the results
— avoiding excessive calls to the article repository and limiting the number of
    long-running aggregation processes.

While it would have been nice to not have to maintain the index file manually,
    there were some good reasons I didn't implement this approach.
Obviously, it would have added unnecessary complexity to the application,
requiring significantly more logic for traversing the article repository while
    scanning for articles and their metadata.
But more importantly, it would have made the application responsible for
    indexing the articles.
The purpose of the application is to display the content as it's provided,
not to manage or curate it.
By keeping the article indexing separate from the application serving my
    website,
the content can be managed independently.
Being independent of my website's application means the index can possibly be
    used by other applications or [web services]
to provide consistent indexing and metadata across clients.

## A Couple of Considerations
Knowing where (and when) the article index would be created was only half the
    problem.
To make the index useful and effective, I needed to give forethought to how
    the index should be structured,
    especially if I'm maintaining the index manually for now.

Since the index is also being maintained externally, outside of the application,
this becomes a [tight coupling] between the application and the content data.
Maintaining the articles and the index separately provides no guarantee that the
    application and the article data will remain compatible
(something I had considered when first [integrating the Markdown articles] into
    the application).
If the index structure needs to change to make it easier to maintain, the
    application may need to be updated;
when new features are added to the article repository, the index may need to be
    updated to provide the necessary metadata.
The simpler the index structure is, the more resilient the relationship between
    the application and the article repository will be,
and the less likely there will be an issue.

### The Page at the End of a Book
The idea of an [index] is nothing new.
Many books include a publishing index at the back to help readers locate
    topics of interest.
Traditionally, this style of index maps keywords
    (*e.g.*, names, places, or abstract concepts)
    to page numbers or sections within the book
— painstakingly compiled by a specialized indexer or the author themselves.
There seemed no reason to reinvent anything here, in [my weblog].

To accomplish my immediate goals of listing articles by category with some basic
    metadata,
the index only needed to map category tokens (or tags; or keywords) to the
    article [slug] (the URL path identifier for each article page).
[Javascript Object Notation (JSON)] is an easy way to represent data with
    key-value pairs and nested structures,
so it made sense to add a simple JSON file to
    [the root of the article repository] to hold the index data.
This index file contains the necessary metadata for every listed article
and assigns each article to one or more categories.

Interestingly, many full-text search engines also use similar indexing
    techniques to map every word in the document corpus to the documents that
    contain them.
Naturally, these indexes are much longer and more complex.
To anticipate incomplete terms or input typos, these search indexes often employ
    techniques, like stemming or prefix matching, to improve search results.
These techniques can be quite effective, but they greatly increase the size and
    complexity of the index.
Maintaining a comprehensive full-text search would require some sort of
    tokenization algorithm to generate an effective index;
    it would be nearly impossible to maintain such an index manually for even a
    small article repository.

### Playing the Meta
Another detail
    I spent some time considering was 
    what [metadata] should be included in the article index and what
    metadata should instead remain only in the article files.
Generally, any element of the metadata
(the article title, author, publication date, meta tags, or descriptive summary)
may or may not be needed to render either the article page or its entry in a
    list;
metadata might be needed to render the article list entry, but not the article
    page itself, or vice versa,
or the metadata might be needed for both contexts.
Displaying the article metadata in both the article list entry and the article
    page might be necessary,
but duplicating this metadata in both the index and the article files is far
    from ideal.
Without processes keeping them both aligned, duplicating the metadata can easily
    lead to inconsistencies.
Maintaining the metadata myself, I wanted to avoid duplication as much as
    possible — but that didn't really work out.

The problem came down to how common metadata
    (the information displayed both in the index and the full article)
is accessed.
It's obvious to include the common metadata in the index data to preclude the
    need to query each article file when rendering every article list entry.
However, this still means that index data must be fetched whenever an article
    page is requested as well, to provide all of the necessary metadata.
Requiring this additional query to retrieve the index on every page request is
    generally bad for performance and reliability,
possibly preventing the page from rendering if the query becomes slow or fails
    altogether.

Since reliability and performance of the application is currently more of a
    concern than the inconvenience of managing redundant metadata,
I reluctantly decided to simply duplicate the common metadata.
The article title and summery (*i.e.*, the abstract) are both included in the
    article index but also are included in the article and abstract files,
    respectively.
While the article repository is still quite small and I have no audience,
the time it takes to maintain the redundant data is negligible,
and small inconsistencies that may arise are not likely to ever be noticed.

This is the strategy for now, at least.
The ultimate conclusion I reached is that a solution for synchronizing the
    metadata across the article repository will be necessary — eventually.
Assuming I keep writing and publishing articles to this weblog, at some point it
    will become too cumbersome to maintain all the metadata myself.
The simplest solution would to add some simple scripts to regularly check for
    inconsistencies between the index and the article files, and resolve
    any discrepancies.
Since the article repository is hosted on GitHub, this could be easily
    implemented with a [GitHub Actions] workflow.
However, I intend to add more interactive features to the article repository
    (*e.g.*, likes and comments) that will require a more sophisticated
    solution.
I envision the article repository will be served from a dedicated weblog service
that will automatically resolve an article's metadata to provide consistency
    across all contexts.

## Capping the Requests
I raise all of these considerations because when designing any effective system,
    it's important to understand how the system will be used.
When querying large sets of data over a network, from a set of documents or any
    other source,
the basic [functional requirements] (what will be requested) is not enough to
    deliver a workable solution.
Knowing how often and in what manner the system will be used (the user
    behaviour) must also be considered
— especially if requested information requires processing or is not otherwise
    trivially available.
In many cases, it's also important to not just think about how you intend users
    to make requests,
but also how [bad actors] (*i.e.*, malicious users) might abuse the system.

Almost immediately after implementing this indexing to display article
    highlights on my [personal website],
the rate limits for retrieving articles from the repository were reached.
It had not occurred to me that every request, including invalid requests for
    non-existent resources ([404s]), would still load all the required
    application data
— including the article index file.
Instead of just being requested for the the dozen or so legitimate requests I
    might get each day,
the index file was being requested hundreds of times per minute.
The persistent bombardment of requests I regularly received from potential
    hackers helping me [scan for vulnerabilities]
was triggered thousands of concurrent requests to the GitHub
    [application programming interface (API)].
This was more than enough to exhaust GitHub's rate limit,
also making all article content and data unavailable across my entire website.
Realizing this mistake, I rushed to quickly
    [implement caching for the index file] and all the other static assets,
limiting the maximum number of requests the application could make to any
    resource within a specified time period.
While there was no damage done,
it was an embarrassing reminder that any networked system really should have
    some [throttling] or other rate-limit protections in place,
regardless of scale.

Despite that initial hiccup, the article index has otherwise served
    (sorry; not sorry) well.
There's still a lot to add.
The articles list are only displayed on the homepage.
I would like to add dedicated article list pages for each category, eventually
    with the ability to filter, search, and sort articles.
There's also a lot of metadata that could be added to timestamp articles and
    give credit to any collaborators (thanks, Ren).[^ren]
That said, the index data provided is more than enough to keep writing and
    publishing articles while I continue to build out the rest of my website.
